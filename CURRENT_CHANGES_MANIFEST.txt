SUMMARY OF CHANGES IN THIS PACKAGE
=========================================

1. FIXED: translateSeoArticleLongform() restoration/repeated-switch
   bugs; added comparison-table and exchange-rate-notice
   localization; wired getUnitDisplayDefinition() into the
   "Understanding the X" paragraph with a dimensionDefinitions
   fallback and a <strong>-preservation fix; added formula-explanation
   paragraph localization.

2. FIXED: unitDefinitions coverage gap — 39 units had a units[id]
   entry but no unitDefinitions[id] translation; added 35 new
   translated entries x 13 languages (455 records), plus a generic
   fallback in getUnitDisplayDefinition() (app.js) that reuses the
   square_meter/cubic_meter translation for any other unit whose raw
   English definition exactly matches the generic
   "Square/Cubic metric area/volume unit." pattern — covering ~50
   more SI-prefixed generated units without duplicating records.

3. FIXED: abbreviated digital-storage *bit URL routing bug —
   resolveUnitAlias() could not match kbit/mbit/gbit/tbit/pbit/ebit
   URL tokens to any unit because only bare symbols existed (which
   collide case-insensitively with the byte-family symbols), causing
   deriveConversionFromPath() to return null and the entire SEO
   article (H1, breadcrumb, hero, FAQ, long-form content) to stay
   unhydrated on ~162 of 254 digital/ pages. Fixed by adding the
   missing aliases to the 6 affected decimal-bit unit entries in
   digitalStorageUnits().
   NOTE: one adjacent pre-existing bug was found but NOT fixed, per
   scope: digital/eb-to-ebit still fails because exabit's symbol
   "Eb" and exabyte's symbol "EB" already collided before this
   session's changes (both lowercase to "eb"), so fromUnit.id equals
   toUnit.id for that specific pair. This needs a separate decision
   about which unit "eb" should resolve to by default.

4. NEW — Unit-scoped localization of "Uses of the X today",
   "History of the X", "X — sources", and the unit-distinction-note
   bold label ("International acre vs. US survey acre." etc.):

   These blocks were previously left in English after a language
   switch even though every other part of the SEO article translated
   correctly (this was reported directly from a live production
   screenshot of area/acres-to-ares/ in Japanese). They are now
   wired into the same runtime translation architecture as everything
   else, via four new top-level keys in each i18n-seo/<lang>.json:
   unitUsesToday, unitHistory, unitSources, unitDistinctionLabel —
   all keyed by unit.id (or, for unitDistinctionLabel, by the same
   pair-key format already used by the existing differenceBetween
   object).

   IMPORTANT — this is a professional-translation content project,
   not a one-time code fix. The English content for each unit is
   real, already-published, researched historical/technical prose
   (not boilerplate) — e.g. kilogram's History section alone is four
   dense paragraphs covering the "grave," the 1795 Kilogramme des
   Archives, the 1889 International Prototype of the Kilogram, and
   the 2019 Planck-constant redefinition. There is no shortcut
   database (the unit_facts/ directory referenced by
   generate_about_section.py was never populated) — each unit's
   authoritative English source must be extracted from its own live
   published page before translation.

   Every consuming call site in app.js checks for the presence of
   translated data AND an exact item-count match against the
   original English content before using it, falling back to leaving
   that block in English otherwise. This means partial coverage is
   completely safe: a unit with no entry yet, or a page pairing a
   covered unit with an uncovered one (e.g. kg-to-lbs, where
   kilogram translates and pound does not yet), degrades gracefully
   with no errors, no duplication, and no partial/broken content.

   COVERAGE IN THIS PACKAGE: 2 of ~190 eligible units are fully
   translated across all 13 languages — acre (the original pilot,
   reported live in Japanese) and kilogram (added as a second,
   larger pilot to prove the architecture on denser content). Both
   have been validated with a full Playwright regression suite:
   - Exact English restoration after en -> zh -> [other langs] -> en
   - No duplication on repeated same-language switches
   - Structural integrity unchanged (link/strong/table/<li> counts)
   - Zero JS errors
   - Arabic and Chinese spot-checked for translation quality, correct
     RTL handling, and exact preservation of every number/date in
     the source facts

   No further app.js changes are needed to extend coverage — adding
   more units is purely a matter of authoring and injecting more
   translated JSON records using this same schema and pipeline.

5. NEW — Localization of the article's lede paragraph ("About
   Converting X to Y" intro), a previously-unhandled THIRD content
   block reported directly from a live production screenshot
   (area/acres-to-ares/ in Chinese). Unlike items 4 above, this
   paragraph is built at generation time from a per-CATEGORY
   connector sentence ("Comparing {A} and {B} is common in <category
   context>.") plus a unit-scoped "primary use" clause about
   fromUnit only ("{A} is most often used for <fact>."). A second,
   more complex template variant (both units get their own
   "typically associated with <context>" clause) also exists on some
   pages but has no recovered source data yet.

   Two new top-level keys: chrome.primary_use_intro_template
   (connector template, {UNIT}/{USE} placeholders), plus
   categoryIntroTemplate (keyed by category.id, {UNIT_A}/{UNIT_B}
   placeholders) and unitPrimaryUse (keyed by unit.id) — the latter
   two currently populated for category "area" and unit "acre" only.

   Safety: the translation only ever applies when the page's real
   original English paragraph is regex-matched against the exact
   one-clause template shape AND its two named units equal
   fromUnit.name/toUnit.name — never a blind text replacement. A page
   using the two-clause variant, or any category/unit without this
   data yet, safely stays in English. Verified live: acres-to-ares/
   and acres-to-square-centimeters/ (category "area", unit "acre")
   now translate correctly; hectares-to-acres/ (two-clause variant)
   correctly stays in English with no partial/wrong output.

   Unrelated pre-existing issue noticed while verifying this (NOT
   fixed, out of scope for what was reported): generated compound
   unit names like "Square Centimeter" render with a stray space in
   some languages (zh: "平方 厘米") — affects the H1 heading too, not
   just this new paragraph. Root cause is in the generic
   prefix+base name composition logic, not in this package's changes.

6. FIXED: a second round of the unitDefinitions coverage gap (see
   item 2 above), reported directly from a live screenshot of
   area/square-inches-to-square-centimeters/ in Chinese — the
   converter's "From definition" box AND the "Understanding Square
   inch" paragraph were both showing raw English because
   unitDefinitions.square_inch did not exist in any of the 13
   languages, and its English text ("A square inch is the area of a
   one-inch square.") does not match the generic square/cubic
   metric-unit fallback pattern from item 2 (it is a unique,
   hand-authored sentence, not SI-prefix boilerplate).

   Rather than fix only the reported unit, ran a full audit of every
   unit with a unique (non-boilerplate) English definition against
   all 13 languages' unitDefinitions coverage, and found 11 more
   units with the identical gap: cubic_inch, cubic_yard, milliradian,
   meter_per_second, foot_per_second, mole_per_liter,
   millimole_per_liter, micromole_per_liter,
   parts_per_million_water, parts_per_billion_water, bushel_wheat.
   All 12 (including square_inch) now have real translated
   definitions added across all 13 languages, no app.js changes
   required (the existing lookup logic already consumes
   unitDefinitions[unit.id] directly).

   Verified live: area/square-inches-to-square-centimeters/ in
   Chinese now shows the translated definition in both places.

   Unrelated pre-existing issue noticed while verifying this (NOT
   fixed, out of scope): that same page's "About Converting" intro
   paragraph uses a third template variant ("Comparing X and Y is
   common in... Specifically: ...") not covered by item 5's
   one-clause-template logic, so it still shows in English there —
   same safe fallback, not a regression, just not yet modeled.

7. FIXED: two more "About Converting" intro-paragraph template
   variants (see item 5), reported directly from a live screenshot of
   area/square-inches-to-square-centimeters/ in Chinese, which was
   still showing "Comparing Square inch and Square Centimeter is
   common in... Specifically: A square inch is the area of a
   one-inch square, and square metric area unit." in English.

   Variant 3 - "Both are <definition> units." - used whenever
   fromUnit and toUnit share the exact same English definition
   (this covers every generated square_*/cubic_* SI-prefix pair,
   e.g. square-millimeters-to-square-micrometers).
   Variant 4 - "Specifically: <A's definition>, and <B's
   definition>." - the generic fallback used when neither unit has
   a primary-use/context fact and the two definitions differ (the
   exact case reported).

   Both variants reuse the SAME translated unit definitions already
   powering the "Understanding X" paragraphs via the existing
   getUnitDisplayDefinition() helper - no new per-unit facts needed,
   only two new connector templates
   (chrome.both_are_units_template, chrome.specifically_intro_template)
   translated across all 13 languages. Same safety discipline as
   everywhere else: each variant is only recognized via a regex match
   against the page's real original English text (unit names AND
   definitions must match fromUnit/toUnit exactly), and only applies
   the translation if getUnitDisplayDefinition() actually returns
   translated text (not the raw English definition echoed back).
   Anything that doesn't match falls back to English exactly as
   before - no regression risk.

   Verified live: area/square-inches-to-square-centimeters/ (variant
   4) and area/square-millimeters-to-square-micrometers/ +
   area/square-nanometers-to-square-picometers/ (variant 3) all now
   translate correctly in Chinese.
